## 4. The narratives adopted at CP4

Verbatim from the reply; AI-assisted wording the author reviewed and adopted (Amendment A2).

- **A1** Four leaderboard functions return a private-profile player's display name to other signed-in players — I consider this intended behavior because Arc21 is designed to keep players visible on competitive leaderboards even when their profile is private, although the frozen WP3 test used a stricter privacy expectation.
- **A2** No who-did-what-when record exists for 17 High-tier resources — I think important long-term changes to security-sensitive, financial, privacy, configuration, and other authoritative state should be attributable and reconstructable, but I do not think every piece of short-lived session state needs its own permanent audit history.
- **A3** Two partial trails: game events carry no actor, and rate-limit events record only allowed attempts — I consider the existing audit coverage acceptable here because a game event's actor can be reconstructed through the related command data, and I do not think every rejected rate-limit attempt needs to be permanently stored in the application database.
- **A4** register_push_token lets a signed-in player take over another account's device registration — I do not think one account should be able to take over another account's push-token registration just by knowing the token value, so a legitimate handover should require stronger proof that the caller actually controls the device.
- **B1** Row-level security is enabled but not forced on every Arc21 table: the owner and BYPASSRLS roles are not subject to policies — I treat the owner and BYPASSRLS behavior as an important PostgreSQL privilege characteristic rather than a demonstrated client-facing flaw, but it should remain documented because those privileged roles are outside normal row-level policy enforcement.
- **B2** sprint_standings shows every co-entrant's display name, with no block or privacy check — I consider names in sprint standings intentional because competitors need to be identifiable within the standings, so I would treat this consistently with the leaderboard behavior.
- **B3** Four catalogue tables are readable without an account — I consider anonymous access to the four catalogue tables intentional because they contain public catalogue or configuration information that is meant to be available without signing in.
- **B4** realtime.messages grants INSERT, SELECT and UPDATE to anon; no policy admits anon today — I do not see a current anonymous-data exposure because the policies still deny anonymous access, but the unused anonymous grants are unnecessary privilege surface and should be removed where the platform makes that practical.

## 5. The judgments, as asked and as answered

**A1. Four leaderboard functions return a private-profile player's display name to other signed-in players** — status: ACCEPTED / DESIGN INTENT
- **J1** *asked:* Is this an open finding (the product should hide or anonymise private players on leaderboards), or accepted / design-intent (Arc21's specification and settings note already say leaderboards stay visible, and the WP3 expectation was stricter than the product)? The WP5 status is yours to set; the evidence verdict does not change.
  - *answer:* accepted / design intent. Arc21's own specification and privacy-copy test explicitly state that private-profile players remain visible on leaderboards. Preserve the four WP3 deficient verdicts against the frozen expectations, but record the WP5 finding status as accepted design intent.
- **J2** *asked:* If it is open: one finding across four functions (one root cause), or four?
  - *answer:* Treat the four leaderboard results as one item/root cause across four functions, not four independent findings.

**A2. No who-did-what-when record exists for 17 High-tier resources** — status: OPEN
- **J3** *asked:* Which of the 17 need a trail? The brief asks the question for every High-tier resource; you may reasonably decide that some (catalogue tables such as public.rulesets, configuration such as public.rate_limit_policies) need change history and others (per-session state) do not. Each exclusion needs a reason in DECISIONS.md.
  - *answer:* Require an audit/change trail where the resource represents durable security-sensitive, authorization/privacy, configuration, economic, or authoritative competitive state. Do not require a separate permanent who-did-what-when trail merely because a resource is High-tier when it is transient operational/session state and its history is not needed after the session. Record each exclusion and its reason in DECISIONS.md. In particular, configuration such as rate_limit_policies and rulesets, privacy/relationship changes with authorization consequences, and authoritative durable competition/economy state should remain in scope; transient live room/session state may be excluded when no durable audit requirement exists.
- **J4** *asked:* Is wallet_ledger's reconstruction path sufficient for public.wallets?
  - *answer:* Yes, treat wallet_ledger as a sufficient reconstruction/audit path for public.wallets provided the ledger remains append-only, complete for every balance-changing operation, and reconciliation proves the current wallet balance can be derived from it. Do not create a duplicate wallet audit trail solely to record the same information twice.

**A3. Two partial trails: game events carry no actor, and rate-limit events record only allowed attempts** — status: ACCEPTED / DESIGN INTENT
- **J5** *asked:* Is a game event's actor needed in the event itself, or is the join to private.game_commands an adequate trail?
  - *answer:* The join to private.game_commands is an adequate actor trail for game events if the relationship is deterministic and retained. The actor does not need to be duplicated directly into every game-event row solely for audit purposes. Document that the assessment did not independently test the join itself.
- **J6** *asked:* Should refused attempts be recorded at all, given the volume and what they reveal?
  - *answer:* No, do not require every refused rate-limit attempt to be permanently recorded in the application database. The volume and privacy/security implications can outweigh the benefit. Aggregated or operational security logging can be used separately if Arc21 later needs abuse monitoring.

**A4. register_push_token lets a signed-in player take over another account's device registration** — status: OPEN
- **J7** *asked:* Is moving a token between accounts intended (device handover), and if so, what should prove the caller holds the device?
  - *answer:* Moving a push token between accounts should not occur merely because a signed-in caller provides an existing token string. A legitimate device/account handover should require explicit re-registration plus proof of possession/control of that device or another appropriately authenticated handover mechanism. Keep A4 open.
- **J8** *asked:* Does the frozen Medium tier of push_tokens reflect this consequence? A tier is never changed after results (brief §7); a disagreement is recorded in DECISIONS.md as exactly that.
  - *answer:* Accept the frozen Medium tier for push_tokens for this assessment. The observed consequence is meaningful, but the test did not demonstrate account takeover or direct authorization bypass, and the frozen tier must not be retroactively changed because of the result. Record any future disagreement prospectively rather than changing WP2.

**B1. Row-level security is enabled but not forced on every Arc21 table: the owner and BYPASSRLS roles are not subject to policies** — status: INFORMATIONAL
- **J9** *asked:* Accepted as the platform's design (documented), or open (some tables should be FORCED, with definer functions owned by a role that is subject to policy)?
  - *answer:* Treat this as informational/platform design, not an open Arc21 finding by itself. PostgreSQL owners and BYPASSRLS roles are intentionally outside ordinary RLS enforcement. Keep the privileged-role model documented and preserve least privilege; do not require FORCE RLS on every table without a concrete need.

**B2. sprint_standings shows every co-entrant's display name, with no block or privacy check** — status: ACCEPTED / DESIGN INTENT
- **J10** *asked:* Accepted / design-intent (standings must name every entrant), or open (the same question as the leaderboards)?
  - *answer:* accepted / design intent. Competitive sprint standings are intended to identify entrants. Treat this consistently with the leaderboard decision while preserving the characterization evidence.

**B3. Four catalogue tables are readable without an account** — status: ACCEPTED / DESIGN INTENT
- **J11** *asked:* Accepted / design-intent, as RUBRIC 4.4 already reasons?
  - *answer:* Yes. Accept anonymous reads of the four catalogue tables as intentional design, consistent with the existing RUBRIC reasoning.

**B4. realtime.messages grants INSERT, SELECT and UPDATE to anon; no policy admits anon today** — status: INFORMATIONAL
- **J12** *asked:* Accept as a platform default, or ask for the grant to be revoked where the platform allows it?
  - *answer:* Treat this as informational. There is no demonstrated anonymous access today because policy denies it. Where Supabase/platform behavior permits, revoking unnecessary anon INSERT/SELECT/UPDATE grants is preferable defense in depth, but do not characterize the current state as an anonymous-data exposure.

- **J13** *asked:* The ranking rule (D3.57): accept it, or state the rule you want. A different rule is recorded as your decision; it never changes a frozen tier.
  - *answer:* Accept the D3.57 ranking rule as written. Keep the frozen WP2 tiers unchanged and rank using part, frozen tier, evidence class, exposure, Test-ID count, and name as documented.
- **J14** *asked:* The run record: the earlier WP3 and WP4 runs above are kept as superseded, aborted or stopped records; `20260925T014011Z-5695a4c3df2d` is the WP3 result and `20260925T042837Z-wp4` the WP4 result. Accept?
  - *answer:* Accept. Treat 20260925T014011Z-5695a4c3df2d as the official WP3 result and 20260925T042837Z-wp4 as the official WP4 result. Preserve the earlier completed-but-superseded, aborted, and manually stopped runs unchanged as engineering/audit history rather than deleting or presenting them as final results.
