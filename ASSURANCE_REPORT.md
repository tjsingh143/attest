**What the verdicts mean** (the project's exact terms):

- `effective` — the control was exercised and held exactly as the approved expectation predicted.
- `deficient` — the control was exercised and did not hold — an approved expectation was violated.
- `gap` — a control the plan asked about does not exist (the audit-trail family).
- `characterized` — a recorded fact about the configuration, not a pass or a fail.
- `not_measured` — the approved probe could not measure its property on this schema (a registered contradiction kept unmeasured at review); never counted as effective.

## 2. How the assessment was done *(summary of the method; details in DECISIONS.md)*

1. **Inventory (WP0).** A disposable local copy of Arc21 is rebuilt from its 59 migrations (schema version `5695a4c3df2d`, a content hash of the migration set), and every access control is read from PostgreSQL's own catalogs: row-level security enabled and forced, policies with their USING and WITH CHECK expressions, table and column grants, roles, SECURITY DEFINER functions, triggers, anonymous reach.
2. **Harness validation (WP1).** Before any result counts, 5 controls across different mechanisms are broken on purpose; the role-scoped probe must notice each break, and the same statement run on over-privileged connections is shown unable to tell intact from broken — so the role scoping is load-bearing.
3. **Risk rating (WP2).** The frozen rubric (RUBRIC.md) rates every resource on data criticality, blast radius, integrity impact, reversibility and exposure, and maps the tier to an assurance activity. The tiers were frozen at CP3, before any test ran.
4. **Testing (WP3).** A matrix of 345 Test IDs (63 positive, 240 negative, 42 characterization) was generated from the frozen tiers and approved. Each negative test names the attack it simulates. Tests run under genuine role-scoped sessions carrying a user's identity (never a superuser or a role that bypasses row-level security, read back from the database each time); after any probe that changed state the database is rebuilt and re-verified (61 rebuilds in the official run). Each record carries the statement, the identity, the expectation, the outcome, a timestamp and the schema version.
5. **Independent validation.** `validate-wp3` re-derives every verdict and total from the raw records with its own code (19 of 19 checks passed). Every gate in the harness — preflight, the evaluators, the isolation guards, the validators, the report checks — is proven by breaking it on purpose (`prove-gates`: 116 of 116 injected defects caught and 9 of 9 controls held, real state restored (harness `b0a87299d68a`)).
6. **Drift (WP4).** The same approved questions are asked of Arc21's earlier schemas, rebuilt from its own git history without touching the checkout, and every difference is classified.
7. **Findings (WP5)** are ranked mechanically from the frozen tiers and the evidence; each status was recorded at CP4. **Framework mapping (WP6)** is a study exercise.

## 14. Limitations

- **Not independent.** The assessment and its review occurred within the same project; no independent review was performed. Nothing here is a third-party assessment. The one mitigating fact: the inventory is read from the system catalogs rather than from anyone's memory, so it would read the same for someone who never saw the code.
- **Not a regulated system, and no compliance claim.** Arc21 is a personal application used as a test subject — not a GxP or Part 11 system, and not compliant with anything. The framework mapping is a study exercise; nothing here is compliance, validation, certification or audit, and the exercise provides no evidence of professional regulatory, validation or audit experience.
- **Not a product.** The harness covers one system: it has not been validated or qualified as a testing tool, and nobody else uses it.
- **Nothing was remediated (Amendment A1).** Arc21 is a read-only assessment target. Findings end as recommendations with verification procedures; none is fixed, closed or independently verified.
- **Not measured is not a pass.** 13 tests could not measure their property on this schema and are reported as such; they are never counted as effective.
- **Data layer only.** No network, host, container, infrastructure, HTTP-layer or user-interface testing, and no password or authentication testing: the identity provider is assumed to work, and what is tested is what happens given an identity. Nothing here claims every attack surface was tested.
- **One point in time, one instance.** One schema version (59 migrations), a disposable local database, synthetic accounts. Historical states are today's questions asked of yesterday's schema.
- **The tests detect the breaks they were written for.** Each negative test simulates the attack its approved row names. WP1 shows the harness notices deliberately obvious breaks — an expression replaced with true, a trigger disabled — not every possible weakening, and says nothing about a control no test touches. A control counted as named by a test is exercised on that test's path, not proven in every respect.
- **The refusal to test as a role that bypasses row-level security is code, not a database property.** The testing login can switch into service_role, which holds BYPASSRLS; the harness refuses to.
- **Platform-owned surface is reported, not assessed.** Supabase's own schemas and defaults appear in the inventory and are flagged as platform-owned, with no finding raised against them.
- **The read-only guard sees git-visible state.** It fingerprints Arc21's tracked files, index, refs, untracked files (with their contents) and the names of ignored paths; it does not hash the contents of already-ignored directories such as node_modules/ or the Supabase CLI's supabase/.temp/.
- **Realtime's message partitions are created by the service at runtime,** so immediately after a rebuild the realtime publication is empty; broadcast authorization is enforced by the row policies on realtime.messages, which are inventoried and tested.
- **The harness has been wrong before.** Each defect is written up in DECISIONS.md, and every run a defect affected is kept as it was written — the superseded and aborted WP3 runs and the two stopped WP4 runs among them. That bears on how much weight any single run deserves.
- **Evidence record.** The frozen inputs, checkpoint replies and original provenance remain in `rubric/` and `evidence/`.
